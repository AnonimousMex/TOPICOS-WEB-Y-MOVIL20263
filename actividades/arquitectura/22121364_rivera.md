## 1. Clasificar la plataforma actual

```text
Panel web / cliente móvil
  → HTTP /entregas/recomendar/
  → proceso Django: urls → views → recomendador → reglas → medios
       ↘ carga del modelo local .joblib
       ↘ base de pedidos
```

Es un **monolito con API**: separar la interfaz del servidor no separa los módulos del backend en unidades de despliegue. La evidencia del ejemplo es que `entregas/views.py` importa el recomendador y ejecuta reglas y medios en memoria; no hay un salto HTTP entre esas responsabilidades. Un `runserver` sirve el proyecto completo. Los nombres corresponden al material docente.

## 2. La trampa de los endpoints

No acepto que tres rutas demuestren microservicios. `/entregas/hola/` y `/entregas/recomendar/` pueden pertenecer al mismo proceso Django. El HTML separado demuestra independencia del cliente. Para hablar de microservicios buscaría procesos con contratos de red y despliegues independientes; no basta contar URLs o contenedores con copias del mismo código.

## 3. La misma operación en dos mundos

**Monolito + API:** una petición llega a la vista, que valida el paquete. El recomendador ejecuta `predict_proba` sobre el modelo local. Las reglas descartan el dron a las 3:00 y recorren el ranking hasta encontrar un medio posible, por ejemplo moto. La fábrica crea su estrategia y devuelve el plan. Son llamadas de Python, no peticiones entre servidores.

**Recomendador separado:** cliente → gateway o entrada de pedidos → Pedidos → HTTP al servicio de recomendación. Este devuelve un ranking versionado; Pedidos valida su contrato, aplica las reglas actuales, construye el medio y registra el pedido. El timeout es un fallo parcial de red nuevo. Si no hay respuesta, Pedidos puede usar una regla de respaldo que compruebe peso, volumen y refrigeración; «moto para todo» no es un respaldo seguro. Si no hay alternativa válida, deja pendiente o rechaza de forma explicada. Un pedido ya guardado sigue consultable.

## 4. Decisión de la empresa

Recomiendo **extraer solo la inferencia de IA**, si el cambio semanal obliga a coordinar despliegues con Pedidos y el equipo puede operar dos servicios.

1. Un modelo de alrededor de 50 MB multiplica memoria por proceso; separarlo permite ajustar sus réplicas sin replicar igual toda la lógica de pedidos.
2. Modelo y dependencias cambian con mayor frecuencia que Pedidos. Un contrato estable permite actualizar el recomendador sin redesplegar la parte transaccional.
3. El costo adicional es concreto: red, timeouts, observación, versiones y respaldo. Hacer solo un corte permite medir ese costo, mientras partir también notificaciones y usuarios no tiene una fuerza demostrada.

Separaría primero el entrenamiento en un proceso fuera de la atención HTTP, incluso si todavía se conserva el monolito. Actualizar un archivo de modelo no exige por definición apagar el servicio: se puede validar un artefacto versionado y cambiarlo de forma controlada.

## 5. Un solo corte

El servicio de recomendaciones posee inferencia, preprocesamiento, versiones de librerías y los `.joblib`. Recibe atributos validados y devuelve ranking, versión del modelo y diagnóstico. No crea folios ni cobra.

Pedidos conserva la vista, las reglas obligatorias del negocio (`reglas.py`), la fábrica y `medios.py`, junto a la persistencia y autorización. Mantener las reglas en Pedidos impide que una versión vieja del modelo autorice un vuelo nocturno. El servicio puede conocer límites para sugerir mejor, pero Pedidos verifica la decisión definitiva.

El límite se define por responsabilidad y ritmo de cambio. Un servicio por cada archivo solo convertiría llamadas locales en dependencias de red, sin independencia útil.
