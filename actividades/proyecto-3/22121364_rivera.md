## Integración del sistema

El objetivo funcional es mantener un solo pedido y un solo folio aunque cambie el cliente. Flutter y React consumen las mismas APIs; la autorización, la selección de medios y los importes definitivos pertenecen al servidor. Así, modificar una regla no exige distribuir versiones distintas en cada pantalla.

El backend se organiza en procesos Python con gateway. FastAPI atiende los servicios operativos y Django sirve inferencia. Los límites se justifican por responsabilidad: Pedidos posee estados y folios, Despacho calcula opciones y asignaciones, e Inteligencia predice y clasifica mensajes. Cambiar de lenguaje o añadir Docker no crea por sí solo esa separación.

## Recomendador y asistente

El recomendador resuelve qué transporte es conveniente a partir de las características del envío. Las reglas eliminan opciones incompatibles antes de aceptar una sugerencia. El asistente interpreta preguntas, consulta datos autorizados y orienta al comprador al cotizador cuando requiere una decisión de transporte.

Los datasets se encuentran separados de las bases operativas. Los modelos se entrenan fuera de las peticiones y se cargan desde artefactos versionados por sus métricas y hashes. Las cifras de evaluación describen datos académicos; no son evidencia de calidad en entregas reales. Las variantes de una frase se separan por grupo para reducir la fuga entre entrenamiento y prueba.

## Patrones que identifico en el código

- **Strategy:** `backend/rumbo/domain.py` concentra variaciones por medio sin repartir condicionales de transporte entre widgets.
- **Adapter:** `backend/rumbo/dispatch_logic.py` y `routing.py` traducen proveedores al contrato interno.
- **Facade:** el registro de Pedidos coordina las operaciones necesarias; `RumboApi` concentra sesión y transporte para Flutter.
- **Repository:** `backend/rumbo/db.py` encapsula consultas parametrizadas y transacciones.
- **Gateway/BFF:** `backend/rumbo/services/gateway.py` mantiene una entrada común y respuestas agregadas por rol.
- **Eventos/Observer:** `runtime.py` y los consumidores desacoplan avisos, estadísticas y cambios de estado. Outbox e idempotencia cubren la entrega y la repetición de eventos.
- **Front Controller:** las rutas de FastAPI y Django realizan el despacho HTTP mediante el framework.

En Flutter la separación entre pantalla, cliente API y servidor cumple la intención de separar presentación y datos, aunque el cliente no implemente MVC clásico. `State` administra la pantalla, `RumboApi` concentra acceso remoto y el servidor conserva las invariantes.

## Web y móvil en la misma Mac

Un emulador Android ejecuta el cliente móvil, mientras el navegador ejecuta la compilación web del mismo proyecto Dart. En web, `localhost` identifica la Mac; en el emulador Android estándar, `10.0.2.2` permite llegar a ese host. En un teléfono físico la API requiere una dirección de red accesible.

El cliente web usa las políticas de cookies y CORS del navegador; el nativo administra su cookie en memoria. La arquitectura del backend y el significado del folio se mantienen. Cambian el transporte, la URL y el empaquetado, no las reglas de negocio.

## Decisiones y límites

El catálogo y el flujo de compra de Flutter son el alcance común de web y Android. Los paneles operativos de React son una interfaz adicional y no sustituyen la demostración Flutter en ambas plataformas. Los pagos de prueba y los recorridos simulados se identifican como tales.

La asignación genética, el seguimiento, los asistentes por rol y las integraciones externas amplían el proyecto. Su utilidad depende de conservar un flujo básico reproducible: buscar, recomendar, registrar, obtener folio y consultar desde el asistente. Una integración externa fallida debe mostrar su límite y no fabricar datos operativos.
